# Agent Baseline Evidence Lab v0.11.0

v0.11.0 turns the repository from an evidence-assessment lab into an end-to-end **Customer Trust Flow** for AI coding-agent workloads.

The release connects governed Docker execution, Agent Baseline evidence, trusted container build verification, SBOM/provenance subject binding, optional Docker Scout policy evaluation, agent-to-artifact lineage, an explicit customer decision, SARIF export and a signed privacy-safe handoff.

The goal is not to manufacture a greener demo. It is to make the complete trust chain reviewable and independently verifiable.

## Headline capability: Customer Trust Flow

The new preferred lifecycle is:

```text
AI coding task
  ↓
Docker Sandbox / governed execution
  ↓
Agent Baseline assessment + assurance
  ↓
agent-modified workspace
  ↓
Docker Buildx OCI artifact
  ├─ SPDX SBOM
  └─ SLSA provenance
  ↓
OCI graph + attestation verification
  ↓
optional Docker Scout evidence / gate
  ↓
agent → workspace → artifact lineage
  ↓
Customer Decision Brief + SARIF
  ↓
signed Customer Trust Handoff
```

Installed entrypoint:

```bash
abl-trust --scout-mode observe
```

Makefile paths:

```bash
make customer-trust-dry-run
make customer-trust SCOUT_MODE=observe
make customer-trust SCOUT_MODE=gate
make customer-trust-mcp SCOUT_MODE=observe
make trust-handoff-verify
```

## Trusted artifact verification

v0.11 adds a dedicated artifact-trust plane rather than treating “image built successfully” as the end of the story.

The verifier checks the OCI representation itself, including:

- descriptor SHA-256 and size;
- runnable image manifest and config relationships;
- referenced binary layers;
- attestation manifests;
- duplicate/unsafe archive member ambiguity;
- SPDX SBOM in-toto statements;
- SLSA provenance statements;
- subject binding to the runnable image manifest.

The project does not accept an `sbom.json` or provenance-looking file name as proof by itself.

## Docker Scout: explicit observation versus gating

Docker Scout is integrated with three explicit semantics:

- `off` — Scout is outside the decision boundary;
- `observe` — Scout evidence is collected but does not independently block the disposition;
- `gate` — the configured Scout policy must pass before `EVIDENCE_READY` is possible.

This prevents an exploratory PoC from silently becoming a production authorization policy, while still supporting a strict gate when that is an agreed customer success criterion.

## Agent → artifact lineage

v0.11 creates a cryptographic lineage statement linking:

```text
agent session
  ↓
verified post-agent workspace digest
  ↓
trusted OCI artifact digest
```

Lineage creation fails closed when:

- the workspace was modified after the recorded agent run;
- the OCI artifact changed after trusted-artifact verification;
- the trusted-artifact chain is not verified.

The lineage statement is independently verifiable and Ed25519-signable.

## Customer Decision Brief

The release adds an evidence-derived decision model with four states:

- `BLOCKED`;
- `CONDITIONAL`;
- `EVIDENCE_READY`;
- `DRY_RUN`.

There is still no synthetic security score.

`EVIDENCE_READY` means the configured PoC evidence boundary was satisfied for that run. It does not mean production authorization, compliance certification or official Docker conformance.

## SARIF integration

Agent Baseline and supply-chain findings can now be exported as SARIF 2.1.0 for ingestion by existing security tooling.

The mapping is conservative: positive `PASS` results are omitted while failures, partial evidence, findings and manual-review states retain explicit severity/note semantics.

## Customer Trust Handoff

The final customer-facing ZIP is manifest-driven, signed and independently verifiable.

It can include:

- portable customer evidence pack;
- nested evidence-pack signature;
- public verification key;
- trusted-artifact statement + signature;
- agent-artifact lineage + signature for live verified runs;
- Customer Decision Brief JSON/HTML + signature;
- SARIF;
- sanitized BuildKit / Docker Scout evidence;
- visual Customer Trust Flow summary.

It explicitly excludes:

- private signing keys;
- raw agent prompts/stdout/stderr;
- host filesystem paths;
- Docker credentials/local Docker state;
- OCI binary image archive/layers;
- unrelated local `.abl` state.

The verifier checks safe ZIP paths, member uniqueness, per-member digest/size, absence of unmanifested content, nested customer-pack verification, nested signatures and lineage signature where present.

## Fail-closed dry-run contract

The safe path is now:

```bash
make customer-trust-dry-run
```

Dry-run deliberately cannot claim:

- live Docker containment;
- live network enforcement;
- a real OCI artifact trust result;
- live SBOM/provenance generation;
- Docker Scout enforcement;
- positive agent-to-artifact lineage;
- provider-side credential revocation.

A dedicated `customer-trust` GitHub Actions workflow exercises and independently re-verifies this contract on every main-branch change and pull request.

## Distribution and release provenance

The v0.11 release pipeline dogfoods the same supply-chain principles used by the PoC.

Before publication it:

1. builds the wheel and source distribution;
2. creates `release-manifest.json` and `SHA256SUMS`;
3. installs the wheel in a clean virtual environment;
4. smoke-tests both `abl` and `abl-trust` entrypoints;
5. generates GitHub Artifact Attestations with SLSA build provenance for the release files;
6. verifies those attestations with `gh attestation verify`;
7. publishes the immutable GitHub Release only after provenance verification succeeds.

Consumers can therefore verify both checksum integrity and repository/workflow provenance.

See `docs/RELEASE_PROVENANCE.md`.

## Claims boundary

v0.11 keeps the project intentionally conservative:

```text
SBOM present          != artifact secure
provenance verified   != code correct
Scout pass            != vulnerability-free / certified
lineage verified      != workload safe
signature valid       != organizational identity
EVIDENCE_READY        != production approval
before/after change   != causality
```

This remains a community implementation, assurance and customer-PoC lab. Its purpose is to make evidence and uncertainty inspectable — not to turn unavailable evidence into confidence.
