# v0.12.0 — Versioned customer acceptance policies

v0.12.0 adds a customer-facing policy layer without changing the underlying evidence semantics.

## Customer policy evaluation

The new `abl-policy` entrypoint evaluates a previously generated Customer Decision Brief against an
explicit versioned YAML acceptance profile.

A profile can constrain:

- acceptable Customer Decision states;
- trusted-artifact status;
- Docker Scout status;
- independent assurance status;
- maximum counts for Agent Baseline `FAIL`, `ERROR`, `PARTIAL`, `MANUAL`, `N/A`, or `PASS`.

The evaluator records a canonical SHA-256 digest of the parsed policy. Changing the policy changes
the digest even when the filename remains unchanged.

## Offline verification

`abl-policy verify` independently recomputes the evaluation from the policy and Customer Decision
Brief and rejects tampering with the recorded result, checks, policy identity, source run, or claims
boundary.

## Example profiles

Two deliberately different examples are included:

- `poc-observe` for exploratory PoCs where documented gaps can remain;
- `enterprise-strict` for a promotion-oriented gate requiring evidence-ready status, verified
  artifact, passing Docker Scout evaluation, successful assurance, and no unresolved partial/manual
  controls.

They are examples only and are not Docker recommendations, compliance standards, or certification.

## Design boundary

Policy does not mutate evidence. The same run can be evaluated against multiple customer profiles,
which makes differences in customer acceptance explicit instead of converting them into synthetic
security scores.
