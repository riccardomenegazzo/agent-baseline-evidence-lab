# v0.14.0 — Artifact-aware customer acceptance

v0.14.0 extends customer-specific acceptance from decision-summary gating to direct verification of the trusted software-supply-chain evidence already carried by the signed Customer Trust Handoff.

## Policy schema v2

Customer policy profiles can now require evidence from `trusted-artifact.json` instead of relying only on the summarized Customer Decision Brief.

Supported artifact-aware requirements include:

- required trusted-artifact check IDs and allowed statuses;
- `sbom_present`;
- `provenance_present`;
- `subject_bindings_valid`.

Missing required artifact evidence fails closed. Duplicate trusted-artifact check IDs are rejected rather than ambiguously resolved.

## New built-in profile

The installed wheel now includes:

```text
builtin:enterprise-supply-chain
```

This example policy requires:

- `EVIDENCE_READY` customer decision;
- trusted artifact `VERIFIED`;
- Docker Scout `PASS`;
- independent assurance `PASS`;
- zero `FAIL`, `ERROR`, `PARTIAL` or `MANUAL` assessment results;
- non-root final image posture;
- runtime `HEALTHCHECK` evidence;
- passing OCI attestation integrity;
- observed SPDX SBOM;
- observed SLSA provenance;
- valid attestation subject bindings.

Built-in policies remain examples only. They are not Docker recommendations, production authorization criteria or compliance standards.

## Evidence binding

New policy evaluations use schema v2 and record the SHA-256 digest of the evaluated trusted-artifact JSON.

Changing the artifact after evaluation changes that digest and causes offline verification to fail.

The policy layer still does not rewrite the customer decision or underlying evidence to manufacture a passing result.

## Customer Acceptance Envelope v2

`abl-accept` now extracts the `trusted-artifact` role directly from the already verified Customer Trust Handoff when evaluating an artifact-aware policy.

The v2 signed acceptance statement binds:

- Customer Trust Handoff SHA-256;
- handoff signature SHA-256;
- Customer Decision Brief SHA-256;
- nested trusted-artifact SHA-256;
- exact customer-policy SHA-256;
- recomputed policy-evaluation SHA-256.

This preserves the generic handoff as policy-neutral evidence while making customer-specific acceptance reproducible and tamper-evident.

## Backward compatibility

The v0.14 verifier continues to verify:

- policy-evaluation schema v1 artifacts from earlier releases;
- Customer Acceptance Envelope schema v1;
- acceptance-statement schema v1.

Newly generated policy evaluations and acceptance envelopes use schema v2.

## Release hardening

The clean-wheel release smoke test now verifies that:

- all three built-in profiles are present in package data;
- `enterprise-supply-chain` can be exported from the installed wheel;
- the exported profile is schema v2;
- an artifact-aware policy can evaluate and independently verify a synthetic non-sensitive evidence fixture using only the installed release.

## Claims boundary

A passing artifact-aware customer policy means only that the exact supplied evidence satisfies the exact supplied policy. It does not prove that source telemetry is complete, establish external signer identity, authorize production, guarantee security or constitute Docker/compliance certification.
