# v0.7 — Trust, MCP governance, and incident response

v0.7 extends the lab from **tamper-evident assessment evidence** into a broader assurance exercise. The design goal is not to turn the repository into a certification product. It is to make more claims independently testable while keeping every remaining trust boundary visible.

## What v0.7 adds

### 1. Portable digital signatures

The lab can sign any exported evidence artifact with an Ed25519 OpenSSH key:

```bash
make trust-keygen
make sign-latest
make verify-latest-signature
```

The signature receipt binds:

- artifact SHA-256;
- detached SSH signature SHA-256;
- public-key SHA-256;
- OpenSSH SHA-256 fingerprint;
- signer identity string;
- signing namespace;
- signing time.

The verifier can require an externally supplied fingerprint. That distinction matters: a signature plus a public key stored beside it proves cryptographic consistency, but not that the key belongs to the expected operator. The fingerprint must be trusted through a separate channel for signer authenticity.

### 2. Optional transparency-log publication

A signed artifact can be submitted to Sigstore Rekor using the SSH signature format:

```bash
make rekor-publish-latest
```

This target is intentionally **not** part of normal CI or the interview demo because it creates a public external log entry. CI exercises the same receipt semantics only in dry-run mode:

```bash
make rekor-dry-run
```

A positive Rekor claim requires the entry upload to succeed and `rekor-cli verify` to verify inclusion.

### 3. Signed baseline-source locks

After fetching the authoritative Agent Baseline source:

```bash
make baseline-sync
make baseline-lock-verify
make baseline-lock-sign
```

The verifier checks that `controls.yaml` still matches the digest and control count recorded in `baseline.lock.json`. The lock itself can then be signed with the same portable signing layer.

This does not make an arbitrary baseline URL authoritative. It makes the exact source bytes used for an assessment independently identifiable once the URL/digest or signing key is externally anchored.

## MCP evidence model

### Runtime registration identity

```bash
make mcp-runtime-dhi
```

The collector uses `sbx mcp inspect` and only claims a registration identity match when a labeled identity URL can be extracted and exactly matches the expected URL.

For OAuth-backed servers it uses `sbx mcp auth status` in machine-readable form. Only status/scope metadata is allowlisted into evidence. Token, secret, password, refresh-token, authorization and credential material are never persisted.

### Evaluation-to-execution chains

```bash
make mcp-action-chains
```

Finalized Docker AI Governance audit records are grouped only when they share both:

- `audit_session_id`;
- `resource_id`.

The chain records whether the lab observed:

- policy evaluation;
- approval-required decision;
- deny/reject decision;
- tool invocation;
- tool execution.

A chain is not automatically attributed to a specific coding task. Exact task attribution still needs the separate run-correlation marker or another cross-system identifier.

### Dynamic gateway restrictions

The reference Cedar policies explicitly restrict `invokePrimordial` for dynamic gateway expansion:

- `mcp-add`;
- `mcp-exec`;
- `mcp-find`;
- `mcp-config-set`;
- `code-mode`.

The strict generic policy additionally demonstrates an explicit `<server>-authorize` primordial forbid.

Static policy analysis remains design evidence unless the organization actually enforces the policy and the relevant runtime decision is observed.

### Direct-MCP bypass boundary

Docker MCP access policy governs requests processed through the MCP Gateway. A client configured directly inside a sandbox can instead reach a remote MCP endpoint as network traffic.

The lab therefore treats the two controls separately:

```text
MCP gateway policy
        +
live network-policy denial for direct endpoint
        =
defense-in-depth evidence
```

```bash
make mcp-bypass-dry-run
```

Dry-run mode deliberately cannot claim that the direct network path is blocked. A positive live claim requires `sbx policy check network` to independently return a deny/block decision for the endpoint.

### Explicit OAuth credential revocation

Removing an OAuth credential is mutating and is never part of `assess`, CI, or the default interview flow.

Contract-only check:

```bash
make mcp-oauth-dry-run
```

Explicit live operation:

```bash
make mcp-oauth-revoke MCP_SERVER=<disposable-oauth-server>
```

The adapter claims revocation only when all of these are observed:

1. the hosted credential is recognized as authorized before the operation;
2. `sbx mcp auth rm` succeeds;
3. a second status observation is recognized as unauthorized/absent.

An ambiguous post-state remains unverified. The claim is limited to Docker-hosted MCP OAuth credentials for that server; it does not imply revocation of unrelated provider sessions, accounts or client secrets.

## Observe: behavior drift and unintended actions

### OBS-03 behavior drift

Create a known-good trace profile:

```bash
make drift-baseline-latest
```

Compare a later run:

```bash
make drift-check-latest
```

The profile tracks evidence already present in the normalized trace:

- network destinations;
- MCP tools;
- event-type counts;
- available numeric totals such as tokens, cost, bytes, duration, CPU or memory when producers supply them.

A difference is called **drift**, not maliciousness. Telemetry completeness remains a separate requirement.

### OBS-04 credential/code co-change detector

```bash
make unintended-latest
```

The detector works only from the changed-path set in the agent-run capsule. It flags a high-risk pattern when a credential-like path and a source-code path change in the same run.

It deliberately does **not** open `.env`, SSH keys, cloud credentials or other candidate secret files. A positive result is a metadata pattern requiring investigation, not proof that a real secret was committed.

## Respond: evidence instead of playbooks

### Component quarantine registry

```bash
make quarantine-latest SANDBOX=<component-id>
```

The registry is append-only. Quarantine and release are separate events, each linked to a source-evidence SHA-256.

The registry proves the decision history. It does not by itself prove technical isolation of the component; runtime containment evidence must remain separate.

### Non-agent fallback

```bash
make fallback-demo
```

The fallback runner executes a declared argv without an AI agent and stores only:

- command argv;
- return code;
- output byte counts;
- stdout/stderr SHA-256.

`agent_used=false` is explicit. `human_review_required=true` also remains explicit: successful automation does not prove that a human performed the required review.

### Incident evidence preservation

```bash
make incident-latest
make incident-verify-latest
```

Before copying an assessment bundle, the incident builder requires it to verify. Optional response evidence and response-link statements are also verified before preservation.

Each source is copied byte-for-byte and hashed before and after copy. The incident directory receives its own per-file SHA-256 manifest.

A typical assurance chain becomes:

```text
agent execution
      │
assessment evidence
      │
response evidence
      │
response-link
      │
fallback / quarantine evidence
      │
incident preservation bundle
      │
incident manifest
      │
Ed25519 signature
      │
externally pinned fingerprint
      │
optional Rekor entry
```

## Schema evolution

v0.7 introduces an artifact schema registry and conservative migrations:

```bash
python -m agent_baseline_lab.schema inspect <artifact.json>
python -m agent_baseline_lab.schema migrate <artifact.json> --output <new.json>
```

The first migration is response-drill v1 → v2. It adds the credential-revocation fields with negative/default values; migration must never invent a positive security claim that did not exist in the original evidence.

## Safe CI contract

CI is deliberately incapable of mutating Docker or OAuth state and incapable of publishing Rekor entries. It does, however, exercise:

- all Python unit tests;
- metadata-only agent dry-run;
- MCP runtime dry-run;
- direct-MCP bypass dry-run;
- OAuth-revocation dry-run;
- response anti-false-claim assertions;
- evidence attack matrix;
- non-agent fallback execution;
- incident preservation and verification;
- real ephemeral Ed25519 signing;
- signature verification against an externally supplied fingerprint value;
- Rekor receipt generation in dry-run mode.

GitHub Actions dependencies are pinned by commit SHA rather than mutable major-version tags.

## What still needs real external evidence

v0.7 intentionally leaves these unclaimed until performed in an appropriate disposable/governed environment:

- a finalized Docker AI Governance MCP evaluation + invocation + execution chain;
- exact correlation of that chain to one coding-agent run;
- a live OAuth revocation against a deliberately disposable authorization;
- a public Rekor entry for a deliberately public demo artifact;
- a signer fingerprint anchored outside the evidence producer boundary.

Those are now evidence-collection tasks, not missing implementation primitives.
