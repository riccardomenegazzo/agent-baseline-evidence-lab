# Release Provenance

Agent Baseline Evidence Lab treats its own distribution pipeline as part of the project's trust story.

Starting with the next release after v0.10.2, the release workflow produces both traditional integrity metadata and GitHub/Sigstore-backed SLSA build provenance for the published artifacts.

> Release provenance describes how a downloadable artifact was produced. It does not claim that the artifact is vulnerability-free, formally verified, certified, or approved for production.

## Published artifacts

Each automated release contains:

```text
agent_baseline_evidence_lab-<version>-py3-none-any.whl
agent_baseline_evidence_lab-<version>.tar.gz
SHA256SUMS
release-manifest.json
```

GitHub Artifact Attestations are additionally generated for all four release files.

## Two verification layers

### Layer 1 — SHA-256 integrity

`SHA256SUMS` lets a consumer verify that the downloaded bytes match the release checksums.

Linux:

```bash
sha256sum -c SHA256SUMS
```

macOS:

```bash
shasum -a 256 -c SHA256SUMS
```

`release-manifest.json` records the project version, release tag, source commit, artifact sizes and SHA-256 digests.

This answers:

> Did I receive the exact bytes described by this release metadata?

It does **not** independently authenticate who produced those bytes.

### Layer 2 — GitHub Artifact Attestations

The release workflow uses GitHub's artifact attestation mechanism to generate SLSA build provenance backed by the GitHub Actions OIDC identity and Sigstore transparency infrastructure.

Verify a downloaded artifact with GitHub CLI:

```bash
gh attestation verify \
  agent_baseline_evidence_lab-<version>-py3-none-any.whl \
  --repo riccardomenegazzo/agent-baseline-evidence-lab
```

The same verification can be run for the source distribution and release metadata:

```bash
gh attestation verify \
  agent_baseline_evidence_lab-<version>.tar.gz \
  --repo riccardomenegazzo/agent-baseline-evidence-lab

gh attestation verify \
  release-manifest.json \
  --repo riccardomenegazzo/agent-baseline-evidence-lab

gh attestation verify \
  SHA256SUMS \
  --repo riccardomenegazzo/agent-baseline-evidence-lab
```

This answers a stronger question:

> Does GitHub's attestation service have verifiable provenance linking this subject to this repository/workflow identity?

## Fail-closed publication order

The release workflow follows this sequence:

```text
main CI succeeds
      ↓
version + release-notes validation
      ↓
wheel + sdist build
      ↓
release-manifest.json + SHA256SUMS
      ↓
clean-environment wheel smoke test
      ↓
SLSA provenance attestations
      ↓
gh attestation verify for every release file
      ↓
GitHub Release publication
```

Publication happens **after** attestation verification. If any release artifact cannot be verified against the expected repository identity, the release is not published.

Existing releases are treated as immutable and are never overwritten by the publisher.

## What the attestation does prove

Successful verification supports the following bounded claims:

- the downloaded artifact digest matches an attested subject;
- the attestation is associated with the expected GitHub repository identity;
- the attestation contains build provenance generated by the release workflow;
- GitHub/Sigstore verification succeeds for that provenance statement.

## What it does not prove

A valid release attestation does **not** prove:

- that every source dependency is safe;
- that the package contains no vulnerability;
- that the GitHub account owner has a particular real-world identity;
- that every upstream action or dependency is trustworthy forever;
- that the package satisfies a compliance framework;
- that the package should be deployed in a particular production environment.

This distinction mirrors the rest of the repository: **authentic provenance is evidence, not certification**.

## Why this matters to this project

The lab verifies SBOM, provenance and artifact lineage for customer PoC workloads. Applying provenance to the lab's own release artifacts avoids an obvious credibility gap:

```text
Project claim: verify the provenance of produced software
                         ↓
Project distribution: also ships with verifiable provenance
```

The implementation therefore uses the same philosophy at two levels:

- **customer workload:** BuildKit/OCI evidence, SBOM, SLSA provenance and agent→artifact lineage;
- **project distribution:** SHA-256 release manifest plus GitHub/Sigstore-backed SLSA build provenance.

## Verification checklist

For a high-assurance download:

1. download the wheel, source distribution, `SHA256SUMS`, and `release-manifest.json` from the same GitHub Release;
2. verify the SHA-256 checksums;
3. inspect the `source_commit` in `release-manifest.json`;
4. run `gh attestation verify` for the artifact you intend to install;
5. install the wheel in an isolated virtual environment;
6. run:

```bash
abl --help
abl-trust --help
```
